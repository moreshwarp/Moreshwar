What a Stale Read Teaches Us About Distributed Systems

A two-replica thought experiment about ordering, convergence, and the promises we make.

Moreshwar Pidadi · AI-assisted editorial draft15 OCT 20268 MIN READ
About this note: This is an AI-assisted educational draft prepared for Moreshwar Pidadi's personal research notebook. It is not peer-reviewed, does not claim original experimental results, and should be reviewed and revised by the named author.

A distributed system is not a single computer that happens to have many CPUs. It is a collection of machines that exchange information under conditions of delay and partial failure. Even the simple question “What value is current?” needs a precise answer.

Two replicas, one apparently obvious question

Imagine two replicas, A and B, initially storing the number zero. A client writes the value one to A. Before the update reaches B, a different client reads from B and receives zero. Is B “wrong”?

It depends on the guarantee the system claims. If the service permits eventually consistent reads, this may be a legitimate intermediate state. If it promised a linearizable read that occurs after a completed write, returning the old value would violate that promise.

t₀A = 0 · B = 0replicas agree
t₁write(A, 1)the new value exists on A
t₂read(B) → 0a stale observation is possible
t₃deliver update → B = 1replicas converge in this simple model

Consistency is a promise, not an adjective

We often call a system “consistent” without defining its observable behavior. A stronger habit is to state what a client is allowed to see and when. Linearizability, sequential consistency, causal consistency and eventual convergence make different claims. Their definitions cannot be substituted for one another.

For example, read-your-writes is a session guarantee: a client should not be forced to observe a state older than its own completed update. A service might offer such a guarantee without offering linearizability for every operation by every client.

Order is not identical to wall-clock time

Leslie Lamport’s work on logical clocks provides a foundational way to reason about an event happening before another without assuming synchronized physical clocks. The happened-before relation captures causality induced by local execution order and messages.

Two events may be concurrent in this relation even if their physical timestamps differ. A correct analysis must first identify the causal and contractual ordering relevant to the application.

How I would test a replication claim

  1. Write the invariant. For example, “A completed read after a completed write must return that write or a later one.”
  2. Specify acknowledgments. Does the system acknowledge a write after one local store, a majority, or every replica?
  3. Inject delays and dropped messages in a controlled test. Record operation histories rather than relying on screenshots.
  4. Check histories against the promised model. A visually plausible sequence is not proof of correctness.
  5. State the failure model. Network partitions, crashes and clock behavior affect the conclusions.
Model limitation

The Replica State Lab on this website deliberately models only a primary, a lagging copy and manual delivery of updates. It does not implement consensus, conflict resolution, quorum protocols or a fault-tolerant database.

The question beneath the abstraction

If a system tells me “your update was saved,” exactly what does that mean? Has it reached stable storage? Has it been replicated? Is it immediately visible on every read path? The word saved sounds simple, but every meaningful guarantee has a mechanism and a cost.

This is the kind of systems problem I want to learn to analyze carefully: not only whether a feature works, but the conditions under which its promise continues to hold.
